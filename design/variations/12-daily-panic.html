Armchair Detective Moves Into iPhone, Rewrites Its Own Screen

Mycroft keeps its brain in your pocket and its hands on your Macs and Linux boxes. When it gets itself wrong, it rolls back.

By V. Kurka · Head Nerd · Open source, Swift, ★ 41 at press time

BRNO — A self-modifying, durable agent has taken up residence on an iPhone, sources close to the phone confirmed. The agent is called Mycroft, after the Holmes brother who stayed in his armchair while others did the legwork. Its loop, its conversation state and its own source code all live on the device.

The legwork goes to hands, a small daemon for macOS and Linux. Pair a machine once and the agent gets files, a shell and supervised jobs that keep running when the phone goes offline. It also drives a Mac, and it asks before it deletes, sends or pays.

Most unusually, Mycroft edits itself. Its behaviour and its whole screen are code that it can change, preview and activate while the conversation carries on. Known-good generations are kept, so a bad idea is one rollback away.

There is voice in every thread, and one chat that never ends: a memory tree folds old messages into short summaries. Asked for comment, the agent rewrote its own dashboard and then put it back.

Beyond the Tool-Calling Loop: How We Built an AI Analyst with Bash, a Mounted Filesystem, and a JSON Renderer

By V. Kurka · 29 April 2026 · an excerpt · the full article

Most AI features built today follow the same recipe: take the Vercel AI SDK, register a handful of tools, write a system prompt, and stream the result into a markdown component. It works. It is also where most teams stop — and where most AI products start to feel limited.

This article walks through the architecture we ended up with for the AI Analyst in Engage, and contrasts it with the more conventional Piper chatbot that lives next door in the same codebase. Both ship in the same product. They are wildly different inside.

Problem one: tool results that flood the context

The first wall you hit is large tool outputs. Imagine a tool that runs a SQL query against the warehouse:

const run_query = tool({
  description: 'Run a SQL query against the warehouse.',
  inputSchema: z.object({ sql: z.string() }),
  execute: async ({ sql }) => {
    const { columns, rows } = await warehouse.execute(sql);
    return { columns, rows }; // <-- 50,000 rows of JSON
  },
});

Whatever the tool returns goes straight into the model's context as the tool result message. A query that returns 50k rows is now 50k rows of JSON sitting in the conversation, on every subsequent turn, paid for in tokens, and pushing earlier reasoning out of the window.

You can paginate. You can truncate. You can summarize. All of these are coping mechanisms — they either lose information or force the model to make decisions about data it cannot see.

The fundamental problem is that tool results are a terrible place to put data. Tool results are great for facts the model needs to reason about next. They are awful for bulk data the model needs to slice, group, count, and chart.
