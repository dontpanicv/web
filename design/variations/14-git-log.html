Don't Panic, V!

“I write code no one wants to read, but everyone needs to have. Data whatever.”

I like knowing how things work — from CPUs and protocols to databases and containers. Almost ten years of building a data platform in production taught me most of it.

Some of it I picked up out of curiosity, the rest by debugging production. The domains that stuck: customer data infrastructure, identity resolution and real-time pipelines.

Now I spend that curiosity on AI: local models, agentic workflows, and getting it all into production for real customers, not just demos.

If I can't explain it to someone else, I don't understand it yet. Teaching is how I verify I actually understand something.

  6. release:Beyond the Tool-Calling Looppost/2026-04-29f11e5f5 · 2026-04-29 · V · merges meiro/ai-analyst

    Release notes · reading view

    Beyond the Tool-Calling Loop: How We Built an AI Analyst with Bash, a Mounted Filesystem, and a JSON Renderer

    Most AI features built today follow the same recipe: take the Vercel AI SDK, register a handful of tools, write a system prompt, and stream the result into a markdown component. It works. It is also where most teams stop — and where most AI products start to feel limited.

    The first wall you hit is large tool outputs. Whatever a tool returns goes straight into the model's context. A query that returns 50k rows is now 50k rows of JSON sitting in the conversation, on every subsequent turn, paid for in tokens, and pushing earlier reasoning out of the window. Tool results are a terrible place to put data.

    The second wall is subtler and arrives earlier: metadata bloat. To answer almost any analytical question the model needs to know what exists, and the naive way to expose that is one inventory tool per kind of thing. The model, being agreeable, calls all of them at the start of every conversation “to orient itself”. There is no grep.

    So the Analyst gets one tool, bash, and a filesystem with the inventory already written to disk:

    const workspace = new Bash();
await workspace.writeFile('/context/inventory.json', JSON.stringify(inventory));
await workspace.writeFile('/context/instructions.md', customInstructions);

    Two more ideas complete it: a SQL execution layer that mounts query results as files instead of returning rows, and a JSON renderer with a predefined component manifest, so the answer arrives as charts and tables rather than a wall of prose.

    Read the full article →

    • one tool: bash, on an in-memory filesystem
    • SQL results mounted as files
    • JSON renderer with a component manifest
    • a dozen inventory tools
    • 50k rows of JSON in the context window
