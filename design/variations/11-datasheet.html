3Description

The VK-1 is a general-purpose head nerd. In its own words: “I like knowing how things work — from CPUs and protocols to databases and containers. Almost ten years of building a data platform in production taught me most of it.”

6Typical application circuits

Four reference designs. Three are open source; the fourth has been in volume production since 2018.

6.1Mycroft

Swift · ★41 · github.com/dontpanicv/mycroft

A self-modifying, durable agent that lives on your iPhone. Brain on the phone, hands on your machines. Named after Mycroft Holmes, the brother who stayed in his armchair.

  • The agent loop, its state and its own source live on the phone.
  • It edits its own behaviour and screen, keeps known-good generations and can roll back.
  • It drives a Mac, has voice in every thread, and one infinite chat with a memory tree.

6.2Golem

TypeScript · github.com/dontpanicv/golem

A family AI assistant and second brain on our own machines. No cloud, no central server. In Prague legend, Rabbi Loew shaped the Golem from clay. This one is made from SQLite and Markdown.

  • One server at home, one app for the whole family: web, iPhone, Android.
  • It remembers: topic briefs and learned facts.
  • It does real work on your machines, and asks before it sends, buys or deletes.

6.3Shadow

TypeScript · github.com/dontpanicv/shadow

A shadow company for your team. Every employee gets a shadow: an agent that reads their Slack and mail, tracks what each conversation asks of them, and helps do the work when asked.

  • Lives in Slack. Stays quiet.
  • Runs on your own server: one SQLite database, Markdown files.

6.4Meiro

Day job since 2018 · meiro.io

Customer data infrastructure. Pipes carries sources, events, identity and destinations. Engage runs audiences, journeys and campaigns. Self-hostable: “AI included, that you own, control and audit.”

  • AI Analyst: an analytical agent built on bash, a mounted in-memory filesystem and a JSON renderer instead of a tool-calling loop. See AN-001.

Application note AN-001

Beyond the Tool-Calling Loop: How We Built an AI Analyst with Bash, a Mounted Filesystem, and a JSON Renderer

V. Kurka · Meiro R&D · excerpt

AbstractThe naive AI SDK + tools + markdown loop runs out of room for analytical agents. Two failure modes push you off it: noisy tool results and metadata bloat. Three ideas replace it.

Most AI features built today follow the same recipe: take the Vercel AI SDK, register a handful of tools, write a system prompt, and stream the result into a markdown component. It works. It is also where most teams stop — and where most AI products start to feel limited.

This article walks through the architecture we ended up with for the AI Analyst in Engage, and contrasts it with the more conventional Piper chatbot that lives next door in the same codebase. Both ship in the same product. They are wildly different inside.

We will start from the naive baseline, identify the two failure modes that pushed us off it (noisy tool results and metadata bloat), and then introduce the three ideas that replaced them: just-bash with an in-memory filesystem, a SQL execution layer that mounts results as files, and a JSON renderer with a predefined component manifest.

2Problem one: tool results that flood the context

The first wall you hit is large tool outputs. Imagine a tool that runs a SQL query against the warehouse:

Whatever the tool returns goes straight into the model's context as the tool result message. A query that returns 50k rows is now 50k rows of JSON sitting in the conversation, on every subsequent turn, paid for in tokens, and pushing earlier reasoning out of the window.

You can paginate. You can truncate. You can summarize. All of these are coping mechanisms — they either lose information or force the model to make decisions about data it cannot see.
