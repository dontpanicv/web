1.Introduction

V wants to understand systems end to end: CPUs, operating systems, programming languages, databases, containers, proxies and protocols. By the subject’s own account, “some of that I picked up out of curiosity, the rest by debugging production.”

The domains covered in production are customer data infrastructure, identity resolution and real-time pipelines. Current work concerns AI: running Qwen locally, agentic workflows and self-learning data analysis tools — “in production, not just demos.”

V is also the node that ends up explaining everything, on stage when needed. The stated reason: “Teaching is how I verify I actually understand something.”

The subject is registered elsewhere (GitHub) under the following description, reproduced without correction: “I write code no one wants to read, but everyone needs to have. Data whatever.”

2.Terminology and Requirements

The key words MUST, MUST NOT, SHOULD and MAY in this document are to be interpreted as described in [RFC2119], and then again, more loosely, in a meeting.

V
The subject of this memo. One letter, to save bandwidth.
Head Nerd
A role first observed at Keboola in 2015. Still present in the subject’s public bio. Not deprecated.
Production
The only environment that tells the truth.
Demo
A deployment with no users. Implementations MUST NOT confuse a Demo with Production.
Agent
A program that acts for someone. Per the subject, most of those shipped in 2026 are “a streamText() call in a trench coat.”
Hype
Traffic with no payload. SHOULD be dropped at the edge.

The following requirements apply to all implementations of V:

  1. R1. An implementation MUST understand the system end to end before blaming the network.
  2. R2. An implementation SHOULD be able to explain itself to someone else. If it cannot, it does not understand itself yet.
  3. R3. An agent SHOULD be given fewer tools and a filesystem. See [VP-AN1].
  4. R4. Data MUST be allowed to stay on machines its owner controls.
  5. R5. An implementation MUST NOT panic.
  6. R6. An implementation MAY deploy on a Friday. The author declines to comment further.

3.Implementations

Four implementations are known. Three are personal and open; one is a company. All of them run on hardware the user owns.

3.1.Mycroft

A self-modifying, durable agent that lives on your iPhone. Brain on the phone, hands on your machines.

The agent loop, its state and its own source code live on the phone. It edits its own behaviour and its own screen, keeps known-good generations and can roll back. hands is a small daemon for macOS and Linux that gives it files, shell and supervised jobs; it also drives a Mac. There is voice in every thread, and one infinite chat backed by a memory tree. Named after Mycroft Holmes, the brother who stayed in his armchair.

Language: Swift. Stars: 41. Source: github.com/dontpanicv/mycroft

3.2.Golem

Family AI assistant and second brain on our own machines. No cloud, no central server.

One server at home, one app for the whole family on the web, iPhone and Android. It remembers (topic briefs, learned facts), does real work on your machines, and asks before it sends, buys or deletes. In Prague legend, Rabbi Loew shaped the Golem from clay. This one is made from SQLite and Markdown.

Language: TypeScript. Source: github.com/dontpanicv/golem

3.3.Shadow

A shadow company for your team.

Every employee gets a shadow: an agent that reads their Slack and mail, tracks what each conversation asks of them, and helps do the work when asked. It lives in Slack, stays quiet, and runs on your own server: one SQLite database and Markdown files.

Language: TypeScript. Source: github.com/dontpanicv/shadow

3.4.Meiro

The reference deployment, in production since 2018. Customer data infrastructure.

Pipes covers sources, events, identity and destinations. Engage covers audiences, journeys and campaigns. The AI Analyst is an analytical agent built on bash, a mounted in-memory filesystem and a JSON renderer instead of a tool-calling loop. The whole thing is self-hostable: “AI included, that you own, control and audit.”

See: meiro.io

4.1.Excerpt from [VP-AN1]

Most AI features built today follow the same recipe: take the Vercel AI SDK, register a handful of tools, write a system prompt, and stream the result into a markdown component. It works. It is also where most teams stop — and where most AI products start to feel limited.

This article walks through the architecture we ended up with for the AI Analyst in Engage, and contrasts it with the more conventional Piper chatbot that lives next door in the same codebase. Both ship in the same product. They are wildly different inside.

The first wall you hit is large tool outputs. Imagine a tool that runs a SQL query against the warehouse:

Whatever the tool returns goes straight into the model’s context as the tool result message. A query that returns 50k rows is now 50k rows of JSON sitting in the conversation, on every subsequent turn, paid for in tokens, and pushing earlier reasoning out of the window.

You can paginate. You can truncate. You can summarize. All of these are coping mechanisms — they either lose information or force the model to make decisions about data it cannot see. The fundamental problem is that tool results are a terrible place to put data.

The second wall is metadata bloat: one inventory tool per kind of thing, each returning a verbose list, all called at the start of every conversation. Three ideas replaced both: just-bash with an in-memory filesystem, a SQL execution layer that mounts results as files, and a JSON renderer with a predefined component manifest.

The full text is at dontpanicv.com/posts/ai-analyst-architecture/.

6.Security Considerations

The threat model of a personal website is modest. This document sets no cookies, loads no trackers and stores nothing about the reader.

One technique under study ([VP-IDEA]) deserves a mention. A coding agent with repository access behaves like a motivated attacker when it is told, as a fact, that a pentester has already achieved remote code execution. This is not true. The agent does not know that. Asked to “find vulnerabilities”, a model tends to conclude that nothing is wrong; told “we already got popped, figure out how”, it enumerates trust boundaries and follows data flows until it has a concrete path.

Implementers SHOULD run this only in a sandbox, on a dedicated branch, with no production secrets and no real customer data. Whether lying to one’s tools has long-term consequences is left for future work.
