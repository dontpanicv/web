Backstory

I want to understand systems end to end: how CPUs execute instructions, how operating systems, programming languages, databases, containers, proxies and protocols all fit together. Some of that I picked up out of curiosity, the rest by debugging production.

What I enjoy most is picking up new technology, understanding how it actually works, and figuring out how to apply it. Right now that means AI — running Qwen locally, building agentic workflows, designing self-learning data analysis tools.

I'm also the person who ends up explaining everything. Teaching is how I verify I actually understand something. If I can't explain it to someone else, I don't understand it yet.

Tome I · 2026-04-29 · excerpt

Beyond the Tool-Calling Loop: How We Built an AI Analyst with Bash, a Mounted Filesystem, and a JSON Renderer

Most AI features built today follow the same recipe: take the Vercel AI SDK, register a handful of tools, write a system prompt, and stream the result into a markdown component. It works. It is also where most teams stop — and where most AI products start to feel limited.

This article walks through the architecture we ended up with for the AI Analyst in Engage, and contrasts it with the more conventional Piper chatbot that lives next door in the same codebase. Both ship in the same product. They are wildly different inside.

We will start from the naive baseline, identify the two failure modes that pushed us off it (noisy tool results and metadata bloat), and then introduce the three ideas that replaced them: just-bash with an in-memory filesystem, a SQL execution layer that mounts results as files, and a JSON renderer with a predefined component manifest.

Problem one: tool results that flood the context

The first wall you hit is large tool outputs. Whatever the tool returns goes straight into the model's context as the tool result message. A query that returns 50k rows is now 50k rows of JSON sitting in the conversation, on every subsequent turn, paid for in tokens, and pushing earlier reasoning out of the window.

You can paginate. You can truncate. You can summarize. All of these are coping mechanisms — they either lose information or force the model to make decisions about data it cannot see. The fundamental problem is that tool results are a terrible place to put data.
