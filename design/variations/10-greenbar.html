Beyond the Tool-Calling Loop: How We Built an AI Analyst with Bash, a Mounted Filesystem, and a JSON Renderer

V. Kurka   ·   2026-04-29   ·   first 60 lines of 412

Most AI features built today follow the same recipe: take the Vercel AI SDK, register a handful of tools, write a system prompt, and stream the result into a markdown component. It works. It is also where most teams stop — and where most AI products start to feel limited.

This works great for operational assistants — “create an audience”, “show me the last failed delivery”. The conversation is short, each tool returns a small, well-shaped object, and the markdown is the answer. It stops working the moment the model needs to think with data.

Problem one: tool results that flood the context

0001 | execute: async ({ sql }) => { 0002 | const { columns, rows } = await warehouse.execute(sql); 0003 | return { columns, rows }; // <-- 50,000 rows of JSON 0004 | }

Whatever the tool returns goes straight into the model's context. A query that returns 50k rows is now 50k rows of JSON sitting in the conversation, on every subsequent turn, paid for in tokens, and pushing earlier reasoning out of the window. You can paginate, truncate, summarize. All of these are coping mechanisms.

Problem two: metadata bloat

To answer almost any analytical question, the model needs to know what exists: event types, attributes, audiences, warehouse tables. Expose that as one list tool per entity and the model, being agreeable, calls all of them “to orient itself”. Tens of thousands of tokens land in context before the question is even processed. There is no grep. this is the good bit

What replaced it

1. just-bash with an in-memory filesystem, so the agent can look things up instead of being told everything.

2. A SQL execution layer that mounts results as files, so data lives next to the model rather than inside it.

3. A JSON renderer with a predefined component manifest, so the answer is a chart and a table rather than a paragraph about a chart and a table.
