Beyond the Tool-Calling Loop

How we built an AI Analyst with bash, a mounted filesystem, and a JSON renderer.

Most AI features built today follow the same recipe: take the Vercel AI SDK, register a handful of tools, write a system prompt, and stream the result into a markdown component. It works. It is also where most teams stop — and where most AI products start to feel limited.

This article walks through the architecture we ended up with for the AI Analyst in Engage, and contrasts it with the more conventional Piper chatbot that lives next door in the same codebase. Both ship in the same product. They are wildly different inside.

The textbook recipe works great for operational assistants — “create an audience”, “show me the last failed delivery”. The conversation is short, each tool returns a small, well-shaped object, and the markdown is the answer. It stops working the moment the model needs to think with data.

The first wall you hit is large tool outputs. Whatever the tool returns goes straight into the model's context. A query that returns 50k rows is now 50k rows of JSON sitting in the conversation, on every subsequent turn, paid for in tokens, and pushing earlier reasoning out of the window. You can paginate. You can truncate. You can summarize. All of these are coping mechanisms.

The second wall is subtler and arrives earlier: metadata bloat. To answer almost any analytical question the model needs to know what exists, and one inventory tool per kind of thing fills the context before the first question is asked.

Three ideas replaced the loop: just-bash with an in-memory filesystem, a SQL execution layer that mounts results as files, and a JSON renderer with a predefined component manifest.

Mycroft

A self-modifying, durable agent that lives on your iPhone. Brain on the phone, hands on your machines.

The agent loop, the conversation state and the agent's own source code live on the phone. It edits its own behaviour and its own screen, keeps known-good generations and can roll back when an edit goes wrong.

hands is a small daemon for macOS and Linux. Pair a machine and the agent gets files, a shell and supervised jobs that keep running when the phone goes offline. It also drives a Mac, has voice in every thread, and keeps one infinite chat with a memory tree.
