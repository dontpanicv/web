Projects

Three agents that run on machines you own, and the data platform that pays for the electricity.

Mycroft

A self-modifying, durable agent that lives on your iPhone. Brain on the phone, hands on your machines.

The agent loop, its state and its own source code live on the phone. It edits its own behaviour and its own screen, keeps known-good generations, and can roll back when an idea turns out to be a bad one.

hands is a small daemon for macOS and Linux that gives it files, a shell and supervised jobs. It drives a Mac, takes voice in every thread, and keeps one infinite chat with a memory tree. Named after Mycroft Holmes, the brother who stayed in his armchair.

Golem

Family AI assistant and second brain on our own machines. No cloud, no central server.

One server at home, one app for the whole family — web, iPhone, Android. It remembers through topic briefs and learned facts, does real work on your machines, and asks before it sends, buys or deletes anything.

In Prague legend, Rabbi Loew shaped the Golem from clay. This one is made from SQLite and Markdown.

Shadow

A shadow company for your team.

Every employee gets a shadow: an agent that reads their Slack and mail, tracks what each conversation asks of them, and helps do the work when asked.

It lives in Slack, stays quiet, and runs on your own server — one SQLite database and a folder of Markdown files.

2026-04-29 Beyond the Tool-Calling Loop: How We Built an AI Analyst with Bash, a Mounted Filesystem, and a JSON Renderer Published
Excerpt
Agents · Architecture

Most AI features built today follow the same recipe: take the Vercel AI SDK, register a handful of tools, write a system prompt, and stream the result into a markdown component. It works. It is also where most teams stop — and where most AI products start to feel limited.

This article walks through the architecture we ended up with for the AI Analyst in Engage, and contrasts it with the more conventional Piper chatbot that lives next door in the same codebase. Both ship in the same product. They are wildly different inside.

We will start from the naive baseline, identify the two failure modes that pushed us off it (noisy tool results and metadata bloat), and then introduce the three ideas that replaced them: just-bash with an in-memory filesystem, a SQL execution layer that mounts results as files, and a JSON renderer with a predefined component manifest.

1. The naive architecture: AI SDK + tools + markdown

The Piper chatbot is the textbook implementation. The server side is essentially a single call:

const stream = await streamText({
  model: google(CHAT_MODEL),
  system: buildSystemPrompt({ baseUrl, disabledFeatureIds }),
  tools: assistantTools,
  messages: modelMessages,
  stopWhen: stepCountIs(20),
});

This works great for operational assistants — “create an audience”, “show me the last failed delivery”, “explain what this attribute does”. The conversation is short, each tool returns a small, well-shaped object, and the markdown is the answer.
